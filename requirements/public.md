# Requirements — Public Site

What the public-facing site (`site/`) should be/do. There is no admin site for this project — the sole editor hand-edits data files directly and reruns the build (see `technical.md` → *Repo & deployment*).

Three features: **Timeline** (`site/index.html`, which also encompasses the Home view — see *Navigation* below for why Home and Timeline are two distinct views sharing one page), **Family Tree**, and **Attendees** (reached as the **Details** view of a specific person, no index page or nav link of its own — it's reached through the Family Tree, click an attending person, or through "Folks ▾" — see *Navigation* below). A fourth, **Spreadsheet**, is a future feature idea, not yet built — see *Future feature ideas* at the end of this doc.

## Terminology

Each day is split into four fixed six-hour segments, officially called **day quarters** (`00-06`, `06-12`, `12-18`, `18-24`). The full-viewport-height slide that shows one day quarter is officially called a **quarter screen**, made of two distinct parts:

- **Day quarter canvas padding** — a blank spacer at the top of the quarter screen, sized to clear the sticky nav/jump bars. It holds no content and is a separate element from the canvas, not extra padding on it.
- **Day quarter canvas** — the actual content: the five arrivals/departures/sleeping/meal/activities rows. No date or time label here — that lives in the nav bar (see *Navigation*). This is the only part that counts as "the canvas" — the padding is explicitly *not* part of it.

Use these terms consistently in code, comments, and docs — not "block"/"block screen", and not "the canvas" to mean the whole quarter screen including its padding.

**`00-06` has no display name.** `06-12`/`12-18`/`18-24` are named Morning/Afternoon/Evening in every place a quarter needs a label (the nav's live label, the jump-to-time panel, the Attendees page's fallback quarter label — see *Navigation* and *Attendees* → *Layout* below) — `00-06` alone is never labeled "Night" in any of these. The reason: night reads as the *tail end* of the day before it, not the start of the one after — someone scrolling from Monday evening into the day's first quarter shouldn't land on a screen that announces itself as "Tuesday Night," since it doesn't feel like Tuesday has started yet. Instead, that quarter is identified by the new day itself: the nav's live label reads plainly "Tuesday," the jump-to-time panel's link for it shows only its bare time range ("12am–6am," no name), and the Attendees page does the same when no `time_range` is set. `00-06` still exists everywhere as data (the quarter key, `structures.json` validation, the time-of-day background) and is still called "Night" in internal design language (`brand-guidelines.md` → *Colours*, the Night background color) — this is a display-text rule only, not a rename of the quarter itself.

## Navigation

The site has **four views** — **Home** (the landing page), **Timeline** (the day-quarter canvas), **Family Tree**, and a person's own **Details** page — and **one single nav bar shape, identical on all four, with no per-view variation and no "you are here" indicator.** Every item behaves exactly the same regardless of which view you're currently on — deliberately simpler than an earlier draft of this section, which gave each item an "active/current-page" state that changed depending on where you were; that turned out to be solving a problem nobody asked for. Home and Timeline are two scroll positions on the same physical page (`site/index.html`, see *Home & Timeline* below), not two separate URLs — but they're still distinct views in every sense that matters: different content, and, via the items below, different ways to deliberately reach each one.

Five items, left to right, the same set on every nav bar, every view:

1. **MC26** — the fixed identity (see *Name* in `brand-guidelines.md`), bold, and also a plain link to Home: clicking it always takes you to the landing page, from anywhere, including from Home itself (a harmless no-op there). The one item with no caret and no secondary behavior.
2. **Timeline** — a **split control**: the label itself is a direct jump to whichever quarter screen is current at the cottage (see *Always the full trip, "now" computed live* below) — the fast path when you already know you want "now," from anywhere on the site, in one tap. Its text reads the static word "Timeline" on every view except while actually scrolled into a quarter screen, where it becomes the live day-quarter label instead (see *Timeline's panel* below) — this is a working feature (the thing you actually scan for while scrolling, per `brand-guidelines.md` → *Typography*) carried over unchanged from before this redesign, not something dropped just because the item now has a second job. A separate caret next to the label opens a panel to choose something else instead — see *Timeline's panel* below.
3. **Folks** — the same split-control shape, for jumping to a *person* instead of a *time*: the label itself takes you to a random attending person's Details page, computed fresh client-side at the moment of the click from the full `attending: true` roster in `shared/data/people.json` — every attending person has a Details page (even one still "Collecting facts," which just shows that status instead of travel facts), so nobody is excluded from the pool. The caret opens a panel to pick a specific person instead — see *Folks panel* below.
4. **Milestones** — a caret-only disclosure, not a split control: unlike Timeline/Folks, there's no single obvious "jump to the one that matters" default action for a list of everyone's travel facts, so the whole "Milestones ▾" label is the trigger, no separate default click. Opens a panel of five plain links, each to its own standalone page under `site/milestones/` — see *Milestones panel* below for the links themselves, and *Milestones* (its own top-level section, below *Attendees*) for what each page actually shows.
5. **Tree** — a plain link to the Family Tree page. No caret, no secondary behavior — the one plain-action item, alongside the fixed identity and the two split controls.

No underline on any nav item — bold weight, color, and this row's own fixed, always-in-the-same-place position at the top of every page are the tappable cue instead, a short enough, same-every-time set of items (MC26, Timeline, Folks, Milestones, Tree) that it reads as "the nav" on sight. The caret on a split control (or Milestones' own whole-label trigger) is the exact same shared component (markup, size, spacing) everywhere it appears, so "there's more to pick here" always looks identical — except while the Timeline panel's own auto-advance is running, the one deliberate exception (see *Timeline's panel* below).

**Closing a panel** — three ways, and all three must work, on every page that has one of these panels (Family Tree and Details pages included, not just `site/index.html`): clicking a link inside it (acts, then closes — see *Timeline's panel*/*Folks panel* below); clicking anywhere outside the open panel (and outside its own trigger); or opening the *other* split control's panel, which closes this one first rather than leaving both open and overlapping on screen at once. A plain `<details>` disclosure does neither of the last two on its own — clicking away does nothing, and opening one leaves any other already-open panel sitting open behind/beside it — so both are explicit behavior (`shared/nav.js`, since Family Tree and Details pages have no other JS of their own to hang this off), not incidental. This is the one thing that must feel instant: no transition/animation on open or close either way (a plain instant show/hide), so closing one panel to open the other, or dismissing a panel you didn't mean to open, never feels like it's fighting you.

### Timeline's panel

Opened by the caret next to the "Timeline" nav item (see above) — the disclosure this project used to call "the current day quarter label." Its live-label behavior is unchanged: while scrolled into a quarter screen, the item's text switches from the static word "Timeline" to two live parts, updated as you scroll (via `IntersectionObserver` in `timeline/shared.js`) — the abbreviated, weekday-first date (e.g. "Wed, Aug 5" — see `shared/trip.py` -> `format_date_abbrev()`), smaller/secondary, then the bare quarter name (e.g. "· Morning"), large/bold/prominent, `00-06` showing just the weekday+date alone with no quarter suffix per *Terminology* above. Kept abbreviated deliberately — this is a single-row control sharing space with three other nav items on a phone, so it drops the weekday down to "Wed" too, unlike the Attendees page's own "Wednesday, Aug 5th" (full weekday, see *Attendees* → *Layout* below), which has the room to spare for that. Reverts to the static "Timeline" text on every other view, where there's no current quarter to report. Inside the panel:

- **The day/quarter jump list** — every day is one row of exactly four link chips, not a day heading line followed by four separate ones below it: the first chip is still `00-06`'s own link (same target as ever), but its label is that day's date, abbreviated — weekday and month both short, ordinal day kept ("Sat, Aug 1st," from `shared/trip.py` -> `format_date_jump()`, not the fuller `format_date_full()` this panel used before) — instead of a bare time range. The day heading is folded directly into this one chip rather than repeated above four others, e.g. "Sat, Aug 1st | Morning | Afternoon | Evening." Abbreviated specifically because this is a compact chip in a dropdown meant to be scanned quickly across up to fifteen rows, not a page with room to spare the way the Attendees page's own day headings have (see *Attendees* → *Layout* below, still full weekday/month there — this panel is the one exception). The other three read just the bare quarter name (no "· 6am–12pm" suffix here anymore either — one tap already tells you which quarter you landed on). Every chip is tinted its own quarter's color — the same Morning/palest → Afternoon → Evening → Night/darkest family the quarter screens and nav bar already use (see `brand-guidelines.md` → *Colours*) — including the date chip, which takes Night's color since it's still literally the `00-06` slot underneath. All four chips share the exact same plain font, weight, and size, the date chip included — despite being structurally a day heading (see `brand-guidelines.md` → *Typography* → *Headlines* for why that would normally mean Limelight), it deliberately stays in the same face as its three siblings: four chips in one row reading as inconsistent styles looked messy, and color alone already marks it as the different one. Present in this panel on every view (Family Tree, Details pages included) — a link straight to a specific quarter is just as useful from off `site/index.html` as on it. No separate "Now" entry here — the Timeline nav item's own label already covers that exact case in one tap, without opening anything.
- **"▶"/"⏸" play/pause** — steps through every screen one at a time: jump to the next screen, pause so there's time to actually read it, jump to the next, pause — not a continuous scroll. Unlike the jump list above, this control only makes sense while actually on `site/index.html` (Home or Timeline view) — there's no scroll sequence to auto-advance through from the Family Tree or a Details page — so it's the one part of this panel omitted on those two pages. The pause length is a single named constant (`PAUSE_MS` in `timeline/shared.js`, currently 1.8 seconds) meant to be retuned freely for a natural rhythm, not a fixed spec value. Mainly a testing/demo aid for checking the full sequence renders correctly. Always starts from wherever you currently are, not the very first screen. While running, native scroll-snap is suspended for the page — repeatedly firing a smooth jump at every screen while mandatory snap stays active is a known bad combination that can leave the page visibly stuck (see `timeline/shared.css`) — and stops the moment you scroll/swipe manually (manual scroll always wins) or reach the last screen, restoring snap either way. This is an intentional, scoped exception to `brand-guidelines.md`'s "no interactivity beyond scrolling and links" principle — see that doc's *Core Principles*.
  - **While running, the Timeline panel's own trigger shows a small running indicator even with the panel closed** — its caret is replaced by "⏸" instead of "▾." This exists because nesting Play inside a closed panel would otherwise make its running state invisible except by reopening the panel — and a permanently-running, invisible auto-advance would violate `brand-guidelines.md`'s own "legible... beats anything visually clever" principle, plus the old top-level toggle's explicit "a permanent, visible control, not hidden." The one deliberate exception to a split control's caret always being the identical shared glyph.

Clicking any link in this panel closes the disclosure after acting — see *Closing a panel* above for the other two ways.

### Folks panel

**One shape, one roster, on every page — no more per-page variants.** Every attending person in `shared/data/people.json`, regardless of whether they have a `timeline/data/travel.json` entry yet, appears identically in this panel whether you open it from Home/Timeline, the Family Tree, or a Details page. Not-attending people are left out, same as the Attendees feature itself.

Each entry is **name** (plain text) plus two links:
- **"Timeline"** — jumps to the quarter screen where this person first appears (their arrival's day+quarter), or the trip's very first quarter screen (Aug 1st) if they have no `arrival` at all. A same-page anchor on `site/index.html`, a cross-page link (`../index.html#qc-...`) everywhere else — same pattern the day/quarter jump panel already uses for this (see *Timeline's panel* above).
- **"Detail"** — goes straight to their Details page.

No status text of any kind (no "Collecting facts," nothing) — a person still missing travel data is simply someone whose "Timeline" link happens to land on the trip's first quarter instead of their own arrival; the panel doesn't narrate that difference. (Their status is still visible elsewhere: the Family Tree box itself, per *Family Tree* → *Layout* below, and their own Details page.)

**Randomized order, freshly shuffled on every page load** — computed client-side, the same list every "Folks" caret on that page shows (not re-shuffled per-caret if a page ever had more than one), so no single person is always first or always last. Stays fixed while you're on the page; opening and closing the panel repeatedly shows the same order until the next navigation or reload.

**A single-column list, one person per row** — not the wrapping multi-column grid this used to be.

Clicking any entry's link closes the disclosure after acting — see *Closing a panel* above for the other two ways.

### Milestones panel

Opened by the "Milestones ▾" nav item (see above — the whole label is the trigger, not a split control). **Five plain links, one per line** (same single-column shape as the Folks panel's own list, not the wrapping row of chips the Timeline panel's jump list uses — these are five substantial named destinations to scan top to bottom, not short interchangeable chips): **Arrivals, Meals, Departures, Arrivals and Departures, All** — in that order, every time, on every page. Each is a real navigation to its own standalone page under `site/milestones/` (see *Milestones* below for what each page shows), not an inline list the way the Folks panel is — plain link click, panel closes itself the same way any cross-page link closes a panel (see *Closing a panel* above), no client-side JS needed for this panel at all.

On a narrow phone width, every nav bar still fits on one line — the Timeline panel's own trigger (where it has content to show) is the item that shrinks/truncates first (down to a minimum width that always shows at least a sliver of text), and every item's own font shrinks slightly, before anything would overflow or disappear entirely.

## Device support

Both features must work well on a computer and on a phone — this is critical, not a nice-to-have, since most family will be checking the Timeline from a phone while traveling. Prefer native browser behavior (CSS scroll-snap, normal scrolling) over custom JS gesture handling, since native scrolling already works correctly on both.

## Structures

The site tracks a fixed list of named physical locations relevant to the trip — where people sleep, and the airports/station travel routes through — so they're referred to consistently everywhere instead of ad-hoc free text.

**`shared/data/structures.json`** — flat array, shared by both features (currently only the Timeline reads it). Validated at build time: an unknown name elsewhere in the data is a build error, not a silently-ignored typo.

```json
[
  { "id": "cottage", "name": "Cottage", "category": "accommodation", "rooms": ["Master Suite", "Green Room", "Blue Room"], "spaces": [{ "kind": "kitchen" }] },
  { "id": "red-shed", "name": "Red Shed", "category": "accommodation", "always_shown": true, "spaces": [{ "kind": "working" }] },
  { "id": "the-field", "name": "The Field", "category": "accommodation", "instances": ["Rachel's camping tent", "old worn out tent", "Caravan", "Brendan's tent", "Kate & Bob's Revel camper van"] },
  { "id": "barbs-cottage", "name": "Barb's Cottage", "category": "accommodation" },
  { "id": "lakes-general-store", "name": "Lakes General Store", "category": "accommodation", "rooms": ["Top Room"] },
  { "id": "sheogue-inn", "name": "Little Shemogue Inn", "category": "accommodation", "rooms": ["Room X", "Room Zed", "Room Y", "Room T", "Room K"] },
  { "id": "halifax-airport", "name": "Halifax Airport", "category": "transit" },
  { "id": "moncton-airport", "name": "Moncton Airport", "category": "transit" },
  { "id": "sackville-station", "name": "Sackville Station", "category": "transit" }
]
```

- `id` — stable slug, never reused or renumbered. A duplicate is a build error.
- `name` — canonical display name; must be referenced exactly by other data (see below).
- `category` — `"accommodation"` (referenced by `travel.json`'s `room`/`room_by_date`/`working_from` fields, grouped in the Timeline's Structures row) or `"transit"` (referenced by `travel.json`'s `hub` field — see *Home & Timeline* → *Data* below). Any other value is a build error.
- `rooms` — optional list of fixed room names within an accommodation structure, **in display order** (e.g. Cottage's `["Master Suite", "Green Room", "Blue Room"]` — Master Suite always renders first, Blue Room last, regardless of alphabetical order or the order anyone happens to book them in). If present, must be non-empty with no duplicates — a build error otherwise. A structure with `rooms` declared is a real, permanent physical place: it and every one of its named rooms always render in the Structures row (empty or not, in that same declared order) for as long as the structure is active (see `active_from`/`active_to` below), never only when someone happens to be assigned there — see *Home & Timeline* → *Structures* → *Nested box display*. Mutually exclusive with `instances` below (a build error if a structure sets both) — most structures need neither, see *Accommodation — single vs. multi-instance* below.
- `instances` — optional list of valid free-text instance names within an accommodation structure that has many real, individually-named instances but no fixed physical rooms (e.g. The Field's `["Rachel's camping tent", "old worn out tent", "Caravan"]`, one per actual tent/caravan people bring). If present, must be non-empty with no duplicates — a build error otherwise. Unlike `rooms`, a structure with `instances` does *not* always render, and has no fixed display order either (each shown instance sorts alphabetically) — each named instance only shows up in the Structures row when someone's actually assigned to it, same occupancy-driven behavior as no list at all. The only thing `instances` adds is validation: a `room` value referencing this structure must match one of the declared instance names exactly (a build error otherwise, e.g. a typo'd `"The Field — Rachels camping tent"` no longer silently creates a second, unlabeled tent) instead of being arbitrary free text. Mutually exclusive with `rooms`.
- `always_shown` — optional boolean, defaults to `false`. The same "always render this structure's box every quarter, even empty" behavior a `rooms` list grants, but for a structure with no fixed sub-rooms to declare (e.g. Red Shed — a real place people are actively at, sleeping or working, but not one with named rooms like Cottage). Independent of `rooms`/`instances`: a structure can set `always_shown` alone (bare outer box, no nested room boxes, occupants listed directly — same display a bare structure-name room value gets today), or combine it with `instances` (outer box always shows; individual instances still only appear nested when actually occupied). Setting it alongside `rooms` is harmless but redundant, since `rooms` already implies it.
- `active_from` / `active_to` — optional ISO dates (inclusive), independently settable. Default to the start/end of the trip window when omitted, so a structure with neither set is active the whole trip (August 1–15) — the common case today. Meant for a structure that only exists for part of the trip (an inn booked for a specific stretch, in the requirements author's own words: "airports will come and go, inns will exist for like a period") — no current structure narrows this yet, but the fields are validated (ISO date shape, `active_to` not before `active_from`) and ready to use. Only affects the "always shown" behavior of a structure with `rooms` or `always_shown` set — doesn't (yet) restrict which dates a `hub`/`vehicle`/free-text `room`/`working_from` reference is allowed on.
- `spaces` — optional list of `{ "kind": <string> }` objects, declaring what *other* kinds of activity a structure supports, beyond sleeping (sleeping stays its own thing — `rooms`/`instances` above — since it already has a richer per-room mechanism that doesn't need folding into this). `kind` must be one of `"kitchen"` or `"working"` today — any other value is a build error — and a structure can't repeat the same `kind` twice. This is the one general mechanism both `working_from` and a meal's kitchen tag are validated against, rather than each having its own bespoke rule: a `working_from` block's `structure` (see *Home & Timeline* → *Data* → `working_from` below) must reference a structure whose `spaces` includes `{"kind": "working"}` — previously any structure name at all was accepted; a `meals.json` entry's optional `structure` (see *Data* → `meals.json` below) must likewise reference a structure whose `spaces` includes `{"kind": "kitchen"}`. A structure can declare both, either, or neither, independent of its `rooms`/`instances`/`always_shown` settings — today Cottage declares `kitchen`, Red Shed declares `working`. Adding a future third kind (e.g. a games room) means adding a new allowed `kind` string here, not a new field.

**Accommodation — single vs. multi-instance:** Little Shemogue Inn declares its own fixed `rooms` list, same mechanism as Cottage — starting with just `["Room X"]` today, grown as more of its rooms come into use. The Field covers multiple actual instances (different families bring their own tent or caravan) — write the specific instance as `"<structure name> — detail"`, e.g. `"The Field — Rachel's camping tent"`. Red Shed has neither a fixed `rooms` list nor `instances`, but is marked `always_shown` (see above) since it's in near-constant use — both for sleeping and for `working_from` (see *Home & Timeline* → *Data* below). A `room` value is valid if it exactly matches an accommodation structure's `name`, or starts with `"<name> — "` followed by free text — *unless* that structure has a `rooms` or `instances` list declared, in which case the text after `" — "` must exactly match one of the declared names (`"Cottage — Blue Room"` is valid, `"Cottage — Anything Else"` is a build error; likewise `"The Field — old worn out tent"` is valid, `"The Field — some other tent"` is a build error until it's added to The Field's `instances` list; same for `"Little Shemogue Inn — Room X"` against its own `rooms` list) rather than being arbitrary free text. A structure without `rooms` or `always_shown` set only ever shows up in the Structures row when someone's actually assigned there (sleeping or working); no permanent box for a declared-but-currently-empty Field instance just because it exists.

**Transit hubs:** Halifax Airport, Moncton Airport, and Sackville Station are the three hubs travel routes through. `arrival`/`departure` each get an optional `hub` field that must exactly match a transit structure's `name` — flight/train numbers and other free text stay in the existing `detail` field.

## Vehicles

The site also tracks a fixed list of named vehicles used for car travel, for the same reason as *Structures* above — consistent naming instead of ad-hoc free text.

**`shared/data/vehicles.json`** — flat array, validated at build time:

```json
[
  { "id": "camry", "name": "White Toyota Camry" },
  { "id": "caravan", "name": "White Dodge Caravan" }
]
```

- `id` — stable slug, never reused or renumbered. A duplicate is a build error.
- `name` — canonical display name, must be referenced exactly.

`arrival`/`departure` each get an optional `vehicle` field that must exactly match a vehicle's `name` (see *Home & Timeline* → *Data* below) — typically used with `"mode": "car"`. Free text (who's driving, route, etc) stays in the existing `detail` field.

## Home & Timeline (`site/index.html`)

### Layout

Nav bar per *Navigation* above — identical on both views, no per-view variation. Below it, a full-screen, swipe/scroll-through experience, in this order:

1. **The Home view** — the landing page: trip title, general info, and a short list of endorsements (see *Endorsements* below) — the structure below doesn't depend on what any of that content ends up being.
2. **The transition screen** — a full-viewport slide, the same shape as a quarter screen, sitting between Home and the actual Timeline content. Offers an explicit choice of where to start scrolling into the trip from, since simply continuing to auto-scroll a visitor onto "now" (the old behavior — see *Always the full trip, "now" computed live* below for why that changed) skips past this decision instead of asking it: **"Jump to now"** (computed client-side, the identical logic the "Timeline" nav item's own click uses — see *Navigation*) and **"Aug 1st"** (a plain anchor to the very first quarter screen, `#qc-2026-08-01-00-06` — since scrolling on past this screen without picking anything already leads there, this option is just a shortcut past the choice itself, not a separate code path).
3. **One quarter screen per day quarter, in order** — the Timeline view, one continuous scroll-through.

All of the above uses CSS scroll-snap on `html` (not `body` — `html`/`documentElement` is the actual scrolling element for the page, so scroll-snap-type must be set there or it silently does nothing) — scrolling or swiping down moves from one screen straight to the next, each filling the whole viewport. `scroll-snap-stop: always` makes one scroll/swipe gesture advance exactly one screen at a time — a fast fling never skips past several unnoticed. `scroll-behavior: smooth` is deliberately NOT used together with scroll-snap here — that combination is a known Safari/iOS bug that can break snapping entirely. This applies the same way on desktop (mouse wheel / trackpad) and mobile (swipe), since it's native browser scroll-snap, not a custom gesture handler.

Each quarter screen is made of the **day quarter canvas padding** (blank spacer, clears the nav bar) followed by the **day quarter canvas** (the actual content) — see *Terminology* above; these are separate elements, not one padded box.

The Family Tree page does *not* use this full-screen snap layout — see *Navigation* above for its nav, and *Family Tree* → *Layout* below for the rest of its page; it's read top-to-bottom normally as a short reference page.

### Endorsements

Below the trip title/subtitle/scroll-hint on the Home view, a short list of quotes from people who've seen the site — a lightweight bit of social proof for anyone landing on it fresh, not a data-driven feature. Each entry is just a quote and a first name, hand-edited directly in `timeline/scripts/build.py` (an `ENDORSEMENTS` constant, same pattern as `PAGE_TITLE`/`TRIP_SUBTITLE`) rather than a JSON data file — there's no per-person structure to validate and no other script needs to read them, so a data file would be pure overhead. Quotes render in the order listed, styled quietly (italic quote, plain attribution) so they read as a small aside under the title, not competing with it.

### Time-of-day background

The whole screen — not just the quarter canvas — carries a background tint signaling its day quarter at a glance while scrolling: a second, ambient, full-bleed cue alongside the nav bar's live text label, not a replacement for it. This covers the full browser viewport edge to edge, including the flanking margins outside the centered content column on a wide screen, and the sticky nav bar itself, which switches to match whichever quarter screen is actually in view as you scroll (the same live-tracking behind the nav's day/quarter label) — a single strip of unchanged color anywhere on screen would break the effect.

| Quarter key | Feel | Color |
|-----------|------|-------|
| `06-12` Morning | Palest | Pale pastel blue |
| `12-18` Afternoon | Light | Light pastel blue |
| `18-24` Evening | Medium | Medium pastel blue |
| `00-06` Night | Dustiest/darkest | Dusty pastel blue — still light enough for Primary text |

One tonal blue family across all four, palest at Morning and darkest at Night, rather than four unrelated hues — see `brand-guidelines.md` → *Colours*.

**A quarter screen at rest is always one single flat color, full stop — never a gradient, never a blended band sitting at its top.** The blend between one quarter's color and the next exists *only* as a genuine scroll-linked effect: it's painted live off the actual scroll position while the viewport is physically moving across the boundary between two *adjacent* quarter screens — a real scroll/swipe gesture, or the auto-advance step (always exactly one screen at a time either way) — and it resolves fully to the incoming screen's own flat color the instant that screen finishes settling into place — see `brand-guidelines.md` → *Materials/Design Language*, which is where this is a deliberate exception, not decoration for its own sake.

**A jump that spans more than one quarter screen suspends this live blend for the whole trip, not just the two ends.** The jump-to-time/jump-to-person panel, the transition screen's "Jump to now"/"Aug 1st" choices, and the "Timeline" nav item's own click can each land anywhere from one screen away to the entire length of the trip away — and a browser's smooth-scroll animation takes roughly the same short duration (well under a second) to cross that distance regardless of how many screens it is. Painting the live blend on every one of those in-between screens during a multi-screen jump means racing through every quarter's color in rapid succession — a strobe effect, not the gentle cross-fade this is supposed to be, and a real flashing-content concern, not just an aesthetic one. So: a jump of exactly one screen still plays the live blend, same as organic scrolling; a jump of more than one screen shows no color changes at all for its duration and settles in a single step directly on the destination's own correct color the instant the jump finishes — same correct end state either way, just without painting the screens crossed in between. Landing on any quarter screen by any means (a hash link, the "Timeline" nav item, the transition screen's choices, a jump-menu click, or just scrolling and stopping) must never show a lingering trace of the previous quarter's color, and must never rapid-flash through unrelated quarters' colors either — both are bugs, not "part of the effect." The quarters cycle in a fixed order, so "the previous quarter's color" for a given screen is always known ahead of time, needing no extra per-day data — but knowing that color doesn't mean pre-painting it into the screen; it's only ever used as one endpoint of the live scroll-position blend. The nav bar's own background is driven by that exact same live value as the canvas beneath it (not a separate calculation — see `timeline/shared.js`), so the two never visibly disagree, at rest or mid-transition. The structure/room boxes (see *Structures* → *Nested box display* below) keep their own always-white/paper background and always-dark text regardless of quarter — only the surrounding canvas and nav bar signal time of day, so a name inside a box is never harder to read on one quarter than another.

Text on top of all this — the canvas's own row labels and the nav bar's live label/actions alike — uses exactly one color, Primary (deep tide blue), on every quarter without exception: all four backgrounds are light enough for it to read cleanly, so there's no separate light-on-dark treatment left in the system — see `brand-guidelines.md` → *Colours*. Nothing distinguishes one nav item's role from another's by color; that's weight and size only, so the whole row always reads as one coherent, evenly-lit system rather than each item's color being whatever felt closest when it was added.

Anything that isn't a specific day/quarter — the Home view (the intro screen, before you've scrolled into a day), the Family Tree page, and the Attendees pages — shares one background instead: Grove, a soft pastel green (see `brand-guidelines.md` → *Colours*). A fifth "place" in the palette alongside the four day-quarter colors, not a plain white default; Primary/Text stay the same dark, high-contrast text used on the other light backgrounds.

### Trip window

August 1–15, 2026, inclusive. Each day is split into four day quarters, always in this order:

| Quarter key | Label |
|-----------|-------|
| `00-06` | 12am–6am *(no name — see Terminology above)* |
| `06-12` | Morning · 6am–12pm |
| `12-18` | Afternoon · 12pm–6pm |
| `18-24` | Evening · 6pm–12am |

### Always the full trip, "now" computed live

Every quarter screen for every day, August 1–15, is always rendered — nothing is ever hidden or omitted from the page based on the date, and the build's output doesn't depend on when it happens to run (see `technical.md` → *Scripts*). "Which quarter is it right now" is instead a client-side question, answered fresh by `timeline/shared.js` every time the page loads — read in the trip's own timezone (Atlantic Time, Murray Corner, New Brunswick), not the visitor's own device timezone, so the answer is always "what's happening at the cottage right now," the same question for everyone regardless of where they're checking from — see *Navigation* → *Timeline's panel* above. Two things happen with this:

- **On load, the page always opens on the Home view** — not "now" — unless the URL already points at a specific quarter screen (a `#qc-...` hash, e.g. someone shared a link to a particular moment), in which case that hash is honored directly and the page opens right there, skipping Home and the transition screen entirely. This is a deliberate change from an earlier version of this site, which auto-scrolled every hash-less load straight onto "now": that made the landing page (general info) unreachable on a fresh visit unless you scrolled *backward* against the grain, and quietly decided "start from now" for every visitor instead of asking. Now, "now" is reached deliberately — one tap away via the "Timeline" nav item from literally anywhere on the site, or one scroll-and-choose away at the transition screen (see *Layout* above) — never auto-selected, but never buried either.
- The "Timeline" nav item's own click, and the transition screen's "Jump to now" option, both compute and land on the same place — clamped to the trip's last quarter screen if "now" is already past August 15 — recomputed fresh at the moment of the click, not baked in at build time (see *Navigation* above).

Because the trip window itself (August 1–15) is fixed data, not something computed from the clock, the same built page stays correct for the whole two weeks with no rebuild or redeploy needed as the trip progresses.

### What each day quarter canvas shows

Content is pinned to the **top-left** of the canvas (not centered) — just the five rows below, in this order, each showing nothing if it has no content for that day quarter. No date or quarter-time label here — that's already shown live in the nav bar (see *Navigation* above), so repeating it on the canvas would be redundant.

#### Row applicability by quarter

This table is the source of truth for how the canvas structurally varies by quarter — as of the Structures row's *always-there structures* behavior (see below), all five rows are now eligible in all four quarters; each simply renders nothing (Arrivals/Departures/Meal/Activities) or just its always-there structures with no one in them (Structures) when there's no further data for that specific day+quarter (see each row's own description below).

| Row | `00-06` Night | `06-12` Morning | `12-18` Afternoon | `18-24` Evening |
|-----|:---:|:---:|:---:|:---:|
| Arrivals | eligible | eligible | eligible | eligible |
| Departures | eligible | eligible | eligible | eligible |
| Structures | eligible | eligible | eligible | eligible |
| Meal | eligible | eligible (breakfast) | eligible (lunch) | eligible (dinner) |
| Activities | eligible | eligible | eligible | eligible |

"Eligible" means the row renders if it has content for that day+quarter, and is omitted if it doesn't (per each row's rule below) — normal data-driven emptiness, not a quarter restriction. Structures was previously the one exception (never shown in `12-18`/Afternoon, since sleeping location didn't seem to matter mid-day) — that restriction is gone: a structure with fixed rooms or `always_shown` set (see *Structures* above) is a real physical place, unaffected by time of day, so it and its rooms now render in every quarter, whether or not anyone's actually associated with it right now.

#### Row-by-row rules

1. **Arrivals** — people whose arrival falls in this exact day+quarter: name, mode (✈️ plane / 🚆 train / 🚗 car), a more precise time estimate if one is set (see `time_range` in *Data* below — otherwise no time shown here, since the quarter itself is already the time context), hub (which airport/station, if set — see *Structures* above), vehicle (if set — see *Vehicles* above), free-text detail (flight/train number, who's driving, etc). Includes a person's `excursion` `return` legs (see *Data* → `excursions` below) alongside their bookend `arrival`, rendered identically — a mid-stay return reads no differently than the original arrival. **Several people sharing the exact same leg render as one combined line, not one line each** — but only when the shared detail actually says something beyond the time (a hub, a named vehicle, free-text detail, or a driver): e.g. four people landing on the same flight, all driven onward by the same person, read as a single "Cynthia, Brendan, Priscilla & Thiago" line, not four repeated near-identical ones. Two people who merely happen to arrive at the same rounded time, with none of that further detail set, are **not** assumed to be the same trip just because the displayed text matches — the one exception is actual partners (reciprocal `partner_id`), who still combine into one line even with nothing but a coincidentally-matching time, since they're known to actually be together. Everyone else in that situation gets their own line despite the identical-looking time. A `dogs` tag (see *Data* → `people.json` → `dogs` above) rides along inline right after whichever name it belongs to, e.g. "Cynthia (+ Zoro)". Omitted if nobody arrives in this day+quarter.
2. **Departures** — same shape, same grouping rule, same omit-if-empty rule, for people leaving in this day+quarter. Likewise includes a person's `excursion` `depart` legs alongside their bookend `departure`.
3. **Structures** — labeled "Structures", not "Sleeping": deliberately reframed away from an overnight-only concept to "who's associated with which structure right now, and why." A building can offer more than one kind of space — Cottage has sleeping rooms *and* a kitchen; Red Shed offers working space (see *Data* → `structures.json` → `spaces` below for how a structure declares which non-sleeping kinds it supports). A structure someone's sleeping at, a structure someone's working from, and a structure a meal is being cooked in all render in the same outer box, but stay visually distinct within it — Working and Kitchen each always get their own labeled sub-box (dashed border, same "different category" signal as `.unassigned-box` and the Family Tree's married-in boxes — see *Nested box display* below), never merged into the sleeping-side name list, so it's never ambiguous whether a name (or a meal) is there for the night, for the day, or just cooking. Four things merged into one row: (a) everyone present on the trip during this quarter (arrived by this quarter, not yet departed, and not away on an `excursion` — see *Data* → `excursions` below), grouped by room/structure — computed from each person's arrival/departure, not entered separately, so updating someone's travel dates automatically updates every day quarter canvas's structure lists; (b) everyone with a `working_from` block covering this exact day+quarter (see *Data* below), shown in that structure's own "Working" sub-box — the same person can appear in two different structure boxes on the same quarter screen (their overnight structure, and wherever they're working from that day), since those are two independent facts, not one; (c) whichever structure this exact day+quarter's `meals.json` entry names, if it names one (see *Data* → `meals.json` below), shown in that structure's own "Kitchen" sub-box — the one piece of this row that isn't about a person's own travel facts at all, since a Kitchen's contents are what's cooking, not who's there; and (d) every accommodation structure with a fixed `rooms` list or `always_shown: true` (see *Structures* above) that's currently active, shown regardless of whether anyone's in it. A person's room can change night to night, or even quarter to quarter within the same day (see `room_by_date`/`room_by_quarter` in *Data* below) — someone moving from the Cottage to the Red Shed partway through shows under the correct room for each affected quarter. The row itself is only omitted if there's truly nothing to show at all — no always-there structure exists yet *and* nobody's present, working, or cooking (shouldn't happen once any structure has `rooms`/`always_shown` set, since that structure alone guarantees the row always has something).

   **Nested box display** — rendered as boxes, matching the same plain-box motif as the Family Tree page's person boxes (see *Family Tree* → *Layout* below), not a flat text list, so a room's structure is visible at a glance rather than read out of a string:
   - One outer box per **structure**, labeled with the structure's name — either because someone's actually associated with it this quarter (sleeping, working, or cooking), or because it has a fixed `rooms` list or `always_shown: true` and is currently active (see *Structures* above), even with nobody in any of its rooms right now. **Boxes render in the order `shared/data/structures.json`'s accommodation entries are written, not alphabetically** — reorder that file to reorder this row; nothing else decides it.
   - A structure with a fixed `rooms` list (only Cottage today) always shows an inner box for *every* declared room, in a fixed order, whether or not anyone's assigned to it this quarter — an empty room box just has no names inside it, it doesn't disappear.
   - A structure *without* a fixed `rooms` list only ever gets an inner box for a specific `"<name> — detail"` value if someone's actually sleeping there this quarter (e.g. The Field's tent/caravan instances) — no permanent placeholder box, since there's no fixed list of what those could be.
   - If a person's `room` is a bare structure name with no `" — detail"` suffix (e.g. `"Little Shemogue Inn"`), there's nothing to nest — the people are listed directly inside that structure's outer box, no inner box. Everyone `working_from` a structure for the quarter instead gets a dedicated "Working" sub-box within that structure's outer box, styled like a room box but dashed — never merged into the plain sleeping-side name list, and never nested under a specific room, since `working_from` names a structure, not a room.
   - A structure a meal is tagged to for this exact day+quarter (see *Data* → `meals.json` below) gets a dedicated "Kitchen" sub-box the same way — dashed like Working, but its content is the meal's own `note` text, not a name list; there's no separate "who's cooking" field, since the Kitchen box exists to say what's cooking, not who is.
   - People with no `room` set at all are grouped into a single plain "Unassigned" box, not nested under any structure. This only applies to the sleeping side — `working_from` always names a structure, and a Kitchen entry does too, so there's no "unassigned" case for either.
   - No third level of box per person — inside the innermost box, people (or, for Kitchen, the meal note) are listed as plain text, not individually boxed. This is a deliberate balance call for a ~27-person roster: two box levels (structure, then room/detail) show real structure without the row turning into boxes-within-boxes-within-boxes. Revisit if the real data makes this row hard to scan once filled in.
   - The structure/detail split for sleeping is parsed from the existing `room`/`room_by_date` string values (already validated against `structures.json` at build time, see *Structures* above); `working_from` blocks and a meal's `structure` tag both contribute directly, since they already name a structure with no string to parse; the always-there behavior comes entirely from `structures.json`'s own `rooms`/`always_shown`/`active_from`/`active_to` fields.
4. **Meal** — a free-text note for this quarter, if one exists — `meals.json`'s own `note` field (e.g. "Lobster boil — Dave grilling"). Omitted if no note is set for this day+quarter in `meals.json`; most likely only `06-12` (breakfast), `12-18` (lunch), and `18-24` (dinner) will ever be filled in, but all four quarters support it. If that quarter's meal entry also sets a `structure` (see *Data* → `meals.json` below), the identical `note` text additionally renders as a "Kitchen" sub-box on the Structures row above, inside that structure's own box (see *Nested box display* above) — the same text, never authored twice.
5. **Activities** — a free-text note for this quarter, if one exists (e.g. "Beach volleyball", "Bonfire at Red Shed"). Same shape and omit-if-empty rule as Meal.

A day quarter canvas with nothing in all five rows still renders inside its own full-screen quarter screen — never collapsed or skipped — so scrolling always advances one quarter screen at a time and the five-part shape stays consistent (see `brand-guidelines.md` → *Signature visual conventions*).

### Data

Several data files, all hand-edited directly (no data-entry scripts):

**`shared/data/people.json`** — shared with the Family Tree and Attendees features. Flat array:

```json
[
  {
    "id": 1,
    "name": "Full Name",
    "generation": 1,
    "parent_ids": [],
    "partner_id": null,
    "attending": true
  }
]
```

- `id` — required integer, unique, stable. Never reuse or renumber an existing id once assigned. A random 6-digit number (100000–999999), not a small sequential counter — picked by hand at creation time (no data-entry script generates this — see `way-of-working.md` → *Editing data*), just checked against the rest of the file for a collision. Chosen over sequential ids specifically so the number itself carries no meaning (arrival order in the file, "who was entered first") — see `birth_order` below for the field that's now load-bearing for display order as a result. Validated at build time: every person needs one, and a duplicate id is a build error.
- `name` — required, non-empty display name. When two or more people in the roster share the same first name, disambiguate by appending the first letter of their last name (e.g. `"Helen S"`, `"Jim S"`) — last names are otherwise never shown. If the same first *and* last name both collide (e.g. a parent and child sharing a full name), use a generational suffix instead — `"Fletcher Sr"` / `"Fletcher Jr"` — since a last-initial adds nothing when it's identical too. If a first name is unique in the roster, use it alone with no letter/suffix. Applies as soon as a second person with that first name is added; go back and add the letter/suffix to the existing person's `name` at that point if it wasn't already disambiguated. Validated at build time: two people can't end up with the exact same `name` string — a build error, not a silent look-alike, since a forgotten disambiguation letter would otherwise make two people indistinguishable everywhere a bare name is shown (Family Tree, "Folks ▾", the Structures row).
- `generation` — required integer, 1 = the eldest generation appearing in the tree, increasing by 1 per generation down. Used only by the Family Tree page. Validated at build time: every person needs one, and — after the tree is built — every person must actually be reachable from a generation-1 root by walking `parent_ids`/`partner_id`; a generation number or `parent_ids` chain that doesn't connect back to a root is a build error rather than a person silently missing from the page.
- `parent_ids` — list of 0–2 ids, this person's parent(s). Used only by the Family Tree page. Validated at build time: at most 2 entries, every id must reference a real person, and nobody can be their own parent.
- `partner_id` — id of this person's spouse/partner, or `null`. Used only by the Family Tree page. Validated at build time: if set, must reference a real person, nobody can be their own partner, and the pairing must be reciprocal — if A's `partner_id` is B, B's `partner_id` must be A.
- `married_in` — optional boolean, defaults to `false`/omitted. `true` marks someone who joined the family by marriage/partnership rather than being a blood descendant (a person with no parents of their own in the tree, e.g. a partner who married a blood descendant). Used only by the Family Tree page, to render them with a visually distinct (dashed-border) box — see *Family Tree* → *Layout* below. Not meant for the founding generation (`generation` 1): they're the root of the tree, not "married in" to anything documented, so leave `married_in` unset even though their `parent_ids` is also empty. Validated at build time: a person can't have both `married_in: true` and a non-empty `parent_ids` — that's a contradiction (someone with documented parents is a blood descendant by definition).
- `attending` — required boolean, no default — a build error if missing or not `true`/`false` on any person. Used only by the Attendees feature (see *Attendees* below): everyone in the family tree is listed there, but only people with `attending: true` appear on the Attendees feature at all, get their own facts page, or get a `timeline/data/travel.json` entry. Validated at build time: `attending: false` combined with an existing `travel.json` entry for that person is a contradiction (a build error) — remove one or the other rather than leaving both in place.
- `birth_order` — optional integer, defaults to that person's own `id` when omitted. Used only by the Family Tree page, to decide top-to-bottom display order among siblings (children of the same parent(s)) and among the top-level roots — lower sorts first (oldest first). This is the one field that exists purely to override display order, because `id` itself can't be reused for that: ids are permanent and never renumbered (see `id` above). **Since `id` is now a random 6-digit number with no relationship to entry order, the old fallback-to-`id` default no longer approximates birth order for a sibling group of more than one** — set `birth_order` explicitly on every member of any sibling group with 2+ people (e.g. `1`/`2`/`3`/`4` for four siblings, oldest first), not just "the one being inserted" the way the old sequential-id convention allowed. A single child with no siblings still needs nothing set. Only meaningful relative to the other people it's actually compared against (the same sibling group, or the other roots) — there's no global numbering scheme across the whole tree. Validated at build time: must be an integer when present.
- `dogs` — optional list of dog names, e.g. `["Zoro"]`. A dog is an attribute of the person bringing it, **deliberately not a person of its own** — no `id`, no `attending` flag, no `travel.json` entry, no Family Tree box, no Attendees page, not counted in the Structures row's room occupancy, not part of `parent_ids`/`partner_id`/`birth_order` at all. It only ever renders as a small tag on its owner: a "+ Zoro" line on that person's own Family Tree box (see *Family Tree* → *Layout* below), and a "Traveling with" note on that person's own Attendees page (see *Attendees* → *Layout* below) — nowhere else. If a dog needs a room/travel fact of its own tracked one day, that's a bigger change (closer to a second class of `travel.json` entry) than this field is meant to cover — this is intentionally the minimal version: a name tag, not a record. Validated at build time: must be a list of non-empty strings when present.
- `standalone` — optional boolean, defaults to `false`/omitted. For a person genuinely **not part of the family** (a friend, a guest with no blood/marriage tie to anyone else in the tree) who still needs to show up on the Family Tree and get their own Attendees page. Everyone else in `people.json` must be reachable from a generation-1 root by walking `parent_ids`/`partner_id` — a build error otherwise, since an unreachable person would otherwise silently vanish from the tree — but that requirement makes no sense for someone with no family connection to begin with, so `standalone: true` exempts them from it. `generation` is optional (and ignored) for a standalone person, since it only exists to place someone within the generational tree structure; `parent_ids`/`partner_id`/`birth_order` should all stay unset (a standalone person isn't nested under anyone or sorted among siblings). Rendered in their own section at the very bottom of the Family Tree page, below the whole generational tree — not as another top-level root alongside generation 1, and not nested anywhere — see *Family Tree* → *Layout* below.

**`timeline/data/travel.json`** — one entry per person who has travel and/or a room assignment:

```json
[
  {
    "person_id": 1,
    "arrival": { "date": "2026-08-02", "quarter": "12-18", "time_range": ["15:00", "15:30"], "mode": "plane", "hub": "Moncton Airport", "detail": "AC 619" },
    "departure": { "date": "2026-08-09", "quarter": "06-12", "mode": "car", "vehicle": "White Dodge Caravan", "detail": "Driving back with the Smiths" },
    "room": "Cottage — Room 2",
    "room_by_date": {
      "2026-08-05": "Red Shed",
      "2026-08-06": "Red Shed"
    },
    "working_from": [
      { "structure": "Red Shed", "start_date": "2026-08-03", "end_date": "2026-08-06" },
      { "structure": "Red Shed", "start_date": "2026-08-07", "end_date": "2026-08-07", "quarters": ["06-12"] }
    ]
  }
]
```

- `person_id` — must match an id in `people.json`. Validated at build time: an unknown id is a build error, not a silently-dropped entry.
- `pending` — optional boolean, defaults to `false`/omitted. `true` marks an entry as still tentative/in progress — the Timeline and this person's own Attendees facts page still render whatever's actually filled in (nothing is hidden), but the Family Tree box keeps showing this person under "Collecting facts" rather than "Facts collected" until it's cleared. Meant for a person whose arrival/departure/room is entered but not yet finalized (e.g. a vehicle marked "TBD" in `detail`) — set it while details are still firming up, then remove it (or set `false`) once they're locked in.
- `arrival` / `departure` — both optional. Omit `arrival` if the person is already at their accommodation before August 1 (they'll show as present from day one, with no arrival row ever rendered). Omit `departure` if they're staying past August 15. If both are set, departure can't be before arrival — validated at build time.
- `arrival_note` — optional free text, only meaningful when `arrival` is omitted. Replaces the generic default text ("Already at the accommodation" — see *Attendees* → *Layout* → *Arrival* below) on that person's own Attendees page with something specific to their actual story, e.g. Jim's `"Never left"` or Helen's `"Has been reading in a chair since an undetermined time"` — for a family member the generic framing doesn't quite fit. Has no effect if `arrival` is also set (that leg's own real arrival text always takes over).
- `date` — an ISO date (`YYYY-MM-DD`), validated at build time; applies to `arrival`/`departure`/`room_by_date` keys everywhere in this file.
- `quarter` — one of the day quarter keys above (`00-06`, `06-12`, `12-18`, `18-24`), validated at build time. Always required on `arrival`/`departure` — the coarse 6-hour bucket a leg is shown/grouped under, independent of whether a finer `time_range` estimate is also set.
- `time_range` — optional `[start, end]` pair of 24-hour `"HH:MM"` times, a finer time estimate than the quarter alone — anywhere from an exact time (`start` equal to `end`, e.g. `["18:00", "18:00"]`) to a narrower window than the full 6-hour quarter (e.g. `["14:00", "16:00"]`). Validated at build time: both times must be valid 24-hour `HH:MM`, `start` not after `end`, and both must fall within the quarter's own window (an exact boundary time like `"18:00"` validates against either adjacent quarter). Omit entirely when only the quarter is known — the full quarter window is shown instead, today's behavior. Shown on both the Timeline (in the Arrivals/Departures rows, alongside hub/vehicle/detail) and the person's own Attendees facts page (replacing the generic quarter label, e.g. `"Sunday, Aug 2 · 3–3:30pm"` instead of `"Sunday, Aug 2 · Afternoon · 12pm–6pm"`) — the same field, not entered twice.
- `mode` — required on every `arrival`/`departure`; one of `"plane"`, `"train"`, `"car"`. Validated at build time — missing or any other value is a build error, not a silently-blank travel-mode icon.
- `hub` — optional; must exactly match a transit structure's `name` in `shared/data/structures.json` (see *Structures* above). Omit for car travel or when no specific hub applies.
- `vehicle` — optional; must exactly match a vehicle's `name` in `shared/data/vehicles.json` (see *Vehicles* above). Typically used with `"mode": "car"`.
- `driver_id` — optional; the `id` of another person in `shared/data/people.json` who's driving this leg (e.g. David driving Rachel to the airport for her departure). Validated at build time: must reference a real person, and can't be the traveler's own id (omit `driver_id` entirely when someone drives themselves — it's only for naming someone *else*). Shown on the Timeline and the traveler's own Attendees page appended to the leg the same way `detail` is, worded for which direction it actually is: **"<driver name> pickup"** on an arrival (or an excursion's `return`) — the driver meeting the traveler at a hub — and **"<driver name> driving"** on a departure (or an excursion's own `depart`) — the driver dropping the traveler off. Unlike every other field on a leg, it's also shown on the *driver's own* Attendees page, as a separate "Driving: <traveler name>'s arrival/departure — …" row (see *Attendees* → *Layout* below, which uses the same pickup/driving wording) — the one piece of data on this page that isn't only ever visible to the traveler it's attached to.
- `detail` — free text, shown as-is.
- `room` — the person's default sleeping location for their whole stay; must be a valid accommodation reference per *Structures* above (an exact structure name, or `"<name> — detail"`). Used to group the Structures row. People with the same resolved room are grouped together.
- `room_by_date` — optional map of ISO date → room, same validation as `room`. Overrides `room` for the specific dates listed, for people who change structures mid-stay. Omit entirely if the person sleeps in the same place their whole visit.
- `room_by_quarter` — optional map of ISO date → `{ <quarter key>: room }`, for the rarer case a person's room changes *within* a single day (see `room_by_date` above, which can only override a whole day at a time). Each quarter's room, same validation as `room`. Resolution order for any exact day+quarter is: `room_by_quarter` for that quarter, if listed → `room_by_date` for that date, if set → `room` (the base default) — so this is a targeted exception layered on top of the other two, not a replacement for them: only list the specific quarter(s) that differ from what the day would otherwise resolve to, the same "only the exceptions" philosophy `working_from`'s own `quarters` narrowing already uses. E.g. Brendan/Priscilla/Thiago spend the `18-24` quarter of their arrival evening in the Red Shed, then move to their usual tent from `06-12` the next morning on — but the pre-dawn `00-06` quarter in between (the same physical night, technically the next calendar date) is still the Red Shed, so that one quarter gets a `room_by_quarter` entry rather than a whole extra `room_by_date` day. Validated at build time: same date-shape and room validation as `room_by_date`, plus each key must be one of the four quarter strings (`00-06`/`06-12`/`12-18`/`18-24`).
- `working_from` — optional list of blocks, each `{ "structure": <name>, "start_date": <ISO date>, "end_date": <ISO date>, "quarters": [<quarter key>, ...] }`, for someone working from a structure during the day rather than (or in addition to) sleeping there — e.g. `{ "structure": "Red Shed", "start_date": "2026-08-03", "end_date": "2026-08-06" }`. Independent of `room`/`room_by_date`: a person can sleep in one structure and work from a completely different one on the same day, and both show up (see *Structures* row above). `structure` must exactly match the name of a structure in `shared/data/structures.json` that declares `{"kind": "working"}` in its `spaces` list (see *Structures* → `spaces` above) — not just any structure name. `start_date`/`end_date` are inclusive, validated as ISO dates with `end_date` not before `start_date`. `quarters` is optional, defaulting to `["06-12", "12-18"]` (morning and afternoon) when omitted — the normal case, e.g. Rachel's Aug 3–6 block — and when given must be a non-empty subset of just those two keys; `00-06`/`18-24` are build errors, since working from a structure isn't a concept this site tracks overnight. A single-day exception within a longer stretch (e.g. Rachel working only the morning of Aug 7, the last day of an otherwise Aug 3–7 stretch) is just its own extra block with a narrower `quarters` list, not a special case — see David and Rachel's entries below for both a multi-block (non-consecutive date ranges) and a narrowed-quarters example.
- `excursions` — optional list of blocks, each `{ "depart": <leg>, "return": <leg> }`, for a person who leaves mid-stay and comes back (e.g. an overnight round trip) — the bookend `arrival`/`departure` fields only capture joining and finally leaving the trip once, so a temporary absence needs its own field. `depart` and `return` are each a full leg — same shape and same validation as `arrival`/`departure` (`date`, `quarter`, `mode` required; `hub`, `vehicle`, `driver_id`, `detail`, `time_range` all optional, same rules as above). Validated at build time: `return` can't be before its own `depart`; both must fall within the person's own `[arrival, departure]` window when those are set; multiple excursions must be in chronological, non-overlapping order (each `depart` no earlier than the previous excursion's `return`). Rendered exactly like the bookend legs: a `depart` shows as an extra Departing row on the Timeline and an extra Departure row on the person's Attendees page, a `return` likewise as Arriving/Arrival — sorted into the same date order as everything else, so an excursion in the middle of a stay reads as "Arrival … Departure … Arrival … Departure" in one continuous timeline, not a separate concept. While away, the person is excluded from the Structures row (not counted present) and from the Attendees page's Sleeping milestones (the stay splits into two milestones with a gap, rather than one contiguous range covering time they weren't actually there) — no separate "away" row for this, since the excursion's own Departure/Arrival rows already say so. Unlike the bookend `arrival`/`departure` (where the calendar date of departure still counts as present, since a real night there always precedes it), the `depart` date of an excursion is always the first away night — there's no quarter exception, since whatever time they leave, they aren't back until the `return` leg. This means the Sleeping-row gap always shows for any excursion that crosses into a new calendar date, however short (e.g. leave one afternoon, return the next evening) — only a same-day round trip (depart and return on the identical date) produces no visible gap.
- `airport_runs` — optional list of blocks, each `{ "depart": <leg>, "return": <leg>, "passenger_ids": [<id>, ...] }`, for a driver ferrying OTHER attendees to or from a transit hub — **deliberately not the same concept as `excursions` above**, even though the leg shape is identical. An excursion is about *this person's own* temporary absence from the trip, so it correctly renders as a real Departure+Arrival pair. An airport run is an errand at the hub, not a personal absence — rendering it with the same Departure/Arrival labels reads as if the driver left and rejoined the trip a second time, which isn't true, so it gets its own single-line "Airport run" fact instead (see *Attendees* → *Layout* below). `depart`/`return` — same shape and validation as `excursions`' own (`date`/`quarter`/`mode` required, `hub`/`vehicle`/`time_range` optional; a `driver_id` on either leg would be meaningless here, since the driver is always this entry's own owner, so it's simply never set, not specially rejected). `passenger_ids` — required, non-empty list of ids from `shared/data/people.json`, who's actually being ferried; a real reference list, not free text, so a typo'd/renamed passenger is a build error rather than a silently stale caption — validated to exclude the driver's own id and to only reference real people. Validated at build time: `return` can't be before `depart`, and both must fall within the driver's own `[arrival, departure]` window when those are set (no chronological-ordering requirement against other airport runs, unlike excursions, since a driver could plausibly make more than one run in either order). Each passenger's own `arrival`/`departure` leg still separately carries `mode`/`hub`/`driver_id` as normal (see `driver_id` above) — an airport run doesn't replace that, it's the driver's own complementary fact about the same event. **Scoped to the Attendees page only, for now** — an airport run does not appear on the Timeline's Arrivals/Departures rows or anywhere else; if that's wanted later, it needs its own design (see `workbench/` for how a scoped addition like this gets tracked if picked up as a follow-on).

**`timeline/data/meals.json`** — keyed by date, then day quarter key, only for quarters that have a meal. Each quarter's value is an object, `{ "note": <free text>, "structure": <optional structure name> }`:
- `note` — free text, shown as-is in the Meal row (see *Meal* above) — e.g. "Lobster boil — Dave grilling".
- `structure` — optional; if set, must exactly match the name of a structure in `shared/data/structures.json` that declares `{"kind": "kitchen"}` in its `spaces` list (see *Structures* → `spaces` above). When set, this same `note` text also renders as that structure's "Kitchen" sub-box on the Structures row for this exact day+quarter (see *Structures* → *Nested box display* above) — the one field on this entry not shown in the Meal row itself. Omit it for a meal with no specific kitchen tie (a picnic, a note that isn't about any one place) — it then only ever shows in the Meal row, same as before this field existed.

```json
{
  "2026-08-02": {
    "12-18": { "note": "Arrival lunch — sandwiches on the dock" },
    "18-24": { "note": "Lobster boil — Dave grilling", "structure": "Cottage" }
  }
}
```

**`timeline/data/activities.json`** — same shape as `meals.json`, keyed by date then day quarter key, only for quarters that have a note:

```json
{
  "2026-08-03": {
    "12-18": "Beach volleyball",
    "18-24": "Bonfire at Red Shed"
  }
}
```

### Empty state

If `travel.json` is empty and no meals or activities are set, the timeline still renders every day quarter canvas as an empty card — never an error, never a blank page.

## Family Tree (`site/family-tree/index.html`)

### Layout

Nav bar per *Navigation* above. Below it, people grouped by `generation` (from `shared/data/people.json`), lowest number first. Within a generation, partners (`partner_id`) are shown paired together; each person/couple's children (people whose `parent_ids` includes them) are shown nested/indented below, stacked top to bottom in `birth_order` order (see *Data* → `birth_order` above — oldest first, falling back to `id` for anyone without one set) — e.g. an older sibling added to the file after a younger one already there (a higher `id`) still needs to render first, which is exactly what `birth_order` is for. The same ordering rule applies to the top-level roots themselves when there's more than one family line at the root.

**No text under any individual name says "Married in," "Collecting facts," or "Not attending" — those three states are communicated visually only** (border style/color, a background tint, opacity), never spelled out under a name the way earlier versions of this page did; the tree is meant to be scanned as a shape (who's connected to whom), not read line by line, and a caption under every third name worked against that. No on-page legend/key explains the convention either — a person's own Attendees page states their status directly where relevant, and the nav's own "Folks ▾" dropdown no longer does (see *Navigation* → *Folks panel* above): it's a jump list now, not a status report. Within the site's plain/no-icon visual language (`brand-guidelines.md`), no icons are used for any of this either — only border style/color, a background tint, and opacity.

Anyone with `married_in: true` is rendered with a dashed border in the secondary (sea glass) color — a blood descendant and someone who joined the family by marriage/partnership are visually distinct at a glance, once you know the convention.

Each person's box also reflects the same states the Attendees feature computes (see *Attendees* → *The two states* below — the Family Tree reads `timeline/data/travel.json` read-only, same as Attendees, purely to compute this; nothing is entered a second time):
- **Facts collected** (attending, has a `travel.json` entry that isn't marked `pending`) — the default box, no extra treatment. This is the expected/common case, so it's the one state that isn't decorated.
- **Collecting facts** (attending, no `travel.json` entry yet, or the entry is marked `"pending": true`) — a sand-tinted background (the accent color, whose documented use is exactly this: a background tint).
- **Not attending** (`attending: false`) — the whole box rendered at reduced opacity (faded).

A person who is both married-in and one of the non-default states shows both signals together (e.g. the dashed sea-glass border plus a faded box) — the two are independent facts about a person and aren't mutually exclusive.

A person with `dogs` set (see *Data* → `people.json` → `dogs` above) gets a small "+ <name>" tag beside their own box — a sibling in the couple's row, not a second line nested inside the box itself — unlike the married-in/collecting-facts/not-attending states above, this is a real piece of content (an actual name), not a status, so it's shown as plain text rather than folded into the visual-only border/tint/opacity language those use. Multiple dogs join with commas ("+ Zoro, Bruno"). A dog is never its own box, never nested as if it were a child, and never appears anywhere else on the tree.

An attending person's box (either non-default state above, or the plain default box) is also a working link straight to their own Attendees page (`site/attendees/<id>.html` — see *Attendees* below) — this is the sole entry point to that feature, which has no index page or nav link of its own. A not-attending person's box stays plain text, not a link, since they have no such page.

**A separate section at the very bottom of the page, below the whole generational tree**, holds anyone marked `standalone: true` (see *Data* → `people.json` → `standalone` above) — a guest with no family connection to anyone else. Each renders as their own plain box (same states/link-to-Attendees-page behavior as everyone else above), one per row, not nested under anything and not paired with a partner — since a standalone person has no `parent_ids`/`partner_id` to begin with. This section is omitted entirely if nobody's marked standalone.

### Purpose

Purely reference — so someone new to the family (a partner, a young cousin) can see where they fit. No editing UI beyond the links to each attending person's own Attendees page.

### Data

Backed by `shared/data/people.json` — see *Home & Timeline* → *Data* above for the file structure — plus a read-only look at `timeline/data/travel.json` for the facts-collected/collecting-facts visual only (see *Layout* above). No separate data file of this feature's own.

## Attendees (`site/attendees/`)

No index page of its own — reached by clicking an attending person's box on the Family Tree, the "Detail" link next to their name in a Folks panel (from any page — see *Navigation* above), or the "Folks" nav item's own direct click, which lands on a random attending person rather than a specific one. The Folks panel itself is a jump list only now, with no status text (see *Navigation* → *Folks panel* above) — organizers checking who's still owed a "what are your plans" conversation use the Family Tree page instead, whose boxes carry the sand "Collecting facts" tint directly (see *Family Tree* → *Layout* below) — there's no dedicated grouped list of its own beyond that.

### Purpose

A per-person summary of someone's own travel/room facts — "what's the summary of my facts, so I can just see my facts as me" — pulled out of the day-by-day Timeline schedule into one place, so a family member can check their own arrival/departure/room without scrolling the whole trip to find themselves. Purely reference, same as the Family Tree — no editing UI, no interactivity beyond the pages themselves. There's no way to actually submit or correct your own facts from this page; that still happens by the sole editor hand-editing `timeline/data/travel.json` (see `way-of-working.md` → *The loop*) — this is a read-only view of that same edit, not a new place to make one.

This feature only covers attending people — anyone with `attending: false` has no page here at all (see the Family Tree for the full family, attending or not).

### Data integrity

This is the load-bearing rule for the whole feature: **a person's facts page shows exactly the same `arrival`/`departure`/`room`/`room_by_date` data already in their `timeline/data/travel.json` entry — nothing is entered a second time for this feature.** Updating someone's travel.json entry updates both the Timeline schedule and their facts page from the same rebuild, so the two can never silently disagree. The only new data this feature introduces is `attending` on `shared/data/people.json` (see *Home & Timeline* → *Data* above) — everything else is a different view of data that already exists.

### The two states

Every attending person in `shared/data/people.json` falls into exactly one of these, computed at build time, never hand-assigned as its own field (not-attending people are excluded entirely — see *Purpose* above). This is what the Family Tree's caption reflects for each attending person's box (see *Family Tree* → *Layout* above) — there's no grouped listing of it on this feature itself anymore:

1. **Collecting facts** — no `timeline/data/travel.json` entry yet, or the entry is marked `"pending": true` (see *Data* → `travel.json` → `pending` below, for partial/tentative data that isn't finalized yet). Gets a facts page — if there's no entry at all it just says their travel details aren't in yet; if there's a pending entry, the page shows whatever's actually been entered so far.
2. **Facts collected** — has a `travel.json` entry that isn't marked pending. Gets a facts page showing their arrival, departure, and room, formatted for reading rather than the Timeline's day-quarter-grouped shape.

### Layout

**`site/attendees/<id>.html`** (one per person with `attending: true`, `<id>` is their stable `shared/data/people.json` id, e.g. `site/attendees/7.html` for David) — nav bar per *Navigation* above (the same five items as every other page: MC26, Timeline, Folks, Milestones, Tree). Below it, the person's name as a heading, then, if `dogs` is set (see *Data* → `people.json` → `dogs` above), a single "Traveling with: <name(s)>" line right under the heading — before the day-grouped timeline, not part of it, since a dog isn't a dated fact. Then:
- If they have no `travel.json` entry and no `driver_id` assignments on anyone else's leg (see *Driving* below): a single line saying their travel details aren't in yet.
- Otherwise, a **single chronological timeline grouped under one day heading per distinct date** (see `attendees/scripts/build.py`'s `render_person_page()`) — not a flat Arrival/Departure/Room breakdown and not one block per kind of fact either. Every fact below (Arrival, Airport run, Sleeping, Working from, Departure, Driving) is collected first and sorted together by date, exactly as before, so a Driving obligation or a Working from day that falls between two Sleeping stretches still reads in its actual place in the trip rather than trailing after a much-later Departure — the only change is that consecutive facts sharing the exact same date are now nested under one **day heading** (bold, Primary color, e.g. "Tuesday, Aug 4" — see `brand-guidelines.md` → *Typography* → *Headlines*, which specifies "Day headings" as their own type-level element) instead of each repeating its own full date. A **ranged** fact — **Sleeping only** — is grouped under the *first* date of its range — the fact line itself still states the full range, only which day heading it sits under is decided by where it starts. **Working from is deliberately not treated the same way**, even though its data is also a date range (see *Data* → `working_from` below): sleeping somewhere is a location that holds *until it changes* (so it reads naturally as one range with a "till" endpoint), while working from a structure is a fact about one specific day — true or not true that day, no different from an Arrival — so it renders as its own line under *every* day heading it covers, one per calendar date in the block, never compressed into a single summarized range the way Sleeping is (see the Working from bullet below). When two facts land on the exact same date, ties under that one heading are ordered by what's actually true, not by which one happens to be entered first in the data: **Arrival, then Airport run, then Sleeping, then Working from, then Departure, then Driving.** This is a causal order, not an arbitrary preference — you can't be asleep or working somewhere before the Arrival that puts you there, and a Sleeping/Working from stretch still running that day always precedes the Departure that ends it. Critically, this applies to *every* occurrence of a given kind of fact, not just the trip's own bookend Arrival/Departure: an `excursion`'s `return` is exactly as much an Arrival as the original arrival is, so a Sleeping milestone that starts the same day someone gets back from an excursion still renders *after* that return, never before it (the excursion's own `depart` is a Departure for this same reason, and would equally have to sort after any Sleeping/Working from stretch ending that day). Getting this wrong — showing "Sleeping" before the "Arrival" that started it — reads as if the person was already there before they arrived, which can't be true.
  - **Every fact renders as one flowing line**, not a three-column row, and always **leads with its label** — "Arrival," "Sleeping," "Departure," whichever kind of fact it is — never the time: for a **point-in-time** fact (Arrival, Departure, Driving), the short **label** (bold, secondary color, e.g. "Arrival," "Departure," "Driving") comes first, then the **time** (bold, Primary — the `time_range` if one is set, e.g. "5:15pm", otherwise the bare day quarter name, e.g. "Afternoon" — `00-06` instead shows just its bare time range, "12am–6am", no name, same rule as the nav's live label — see *Terminology*), then the **detail** — "Arrival 5:15pm by 🚗 Car," not "5:15pm Arrival by 🚗 Car." A **date-range** fact (Sleeping) has no single time of day to lead with, so its line just starts at the label too, same as it always has — same for **Working from**, which also has no leading time despite being a repeated per-day fact rather than a range (see the Working from bullet below for that distinction). Label-first is what makes this page scannable as "what happened" first, "when" second, rather than the reverse — it's the same reason every other kind of fact on this page (Sleeping, Working from) already started at the label; point-in-time facts were the one inconsistency. Every date on this page — the day heading and any inline "till..." mention alike — is the same natural-speech form: full weekday, abbreviated month, ordinal day (e.g. "Wednesday, Aug 5th," not "Wed, Aug 5" or "Aug 5") — see `shared/trip.py` -> `format_date_full()`. Weekday stays spelled out (that's the piece someone checking their own facts scans for first); the month shortens to match every other date on the site, which was already abbreviating it. The Timeline's own live nav label and jump-to-time panel go a step further and abbreviate the weekday too, since those are genuinely tight on space in a way this page isn't (see *Navigation* -> *Timeline's panel* above). A room reference always keeps its full stored name, em-dash included (e.g. "Cottage — Master Suite"), matching how it's written in `travel.json` and shown everywhere else on the site (the Timeline's own Structures row).
  - **Arrival** — label first, then time: as above. Detail: `"by <mode tag+name>"` (e.g. "by 🚗 Car"), then hub/vehicle/free-text detail/driver, then who else is on it (see "with `<names>`" below), each appended after an em-dash — e.g. "**Arrival** 5:15pm by 🚗 Car — White Toyota Camry". If `arrival` is omitted: no leading time, detail reads the entry's own `arrival_note` if one is set (see *Data* → `arrival_note` above, e.g. Jim's "Never left"), otherwise the generic default "Already at the accommodation" (grouped under an August 1 day heading, sorting as if dated August 1, whichever text is shown).
  - **"with `<names>`"** — a trailing clause on an Arrival/Departure (and an excursion's own `depart`/`return`, which are exactly those two facts occurring mid-stay), naming everyone else actually on the same flight/train/car — e.g. Wes's departure reads "by 🚆 Train — Sackville Station — with Evey, Helen P & David M". Matched on the leg's STRUCTURAL fields only (mode, hub, vehicle, date, quarter, `time_range`) — deliberately *not* the free-text `detail` or `driver_id` the Timeline's own Arriving:/Departing: row combining rule also requires (see *Home & Timeline* → *Row-by-row rules* → *Arrivals* above): that rule controls whether several people render as one Timeline line or several, a density concern, not this page's "who am I actually traveling with" question — a rental-car-return note only one of two people on the same train has doesn't mean they're on different trains, so it doesn't break this match the way it splits their Timeline line. `time_range` IS part of the match, though (unlike `detail`) — two flights landing in the same broad quarter but at genuinely different times aren't the same trip just because they share a hub. Same coincidental-bare-time guard as that Timeline rule, too: with no hub/vehicle on the leg to point to, only actual partners (reciprocal `partner_id`) still count as traveling together, not anyone whose time merely happens to match. Omitted when nobody else matches. Never shown on the Driving line (see *Driving* below) or the Airport run line, both of which already name their own passengers/travelers directly.
  - **Airport run** — label first, then a *time range*, unlike every other point-in-time fact above (depart time–return time, e.g. "5pm–6pm") — the one exception to "time is a single moment," since a run genuinely spans both ends and rendering it as two separate point-in-time lines is exactly what this fact exists to avoid (see *Data* → `airport_runs` above). Detail: `"by <mode tag+name>"`, then hub/vehicle/free-text detail (same as Arrival/Departure), then who's being ferried — e.g. "**Airport run** 5pm–6pm by 🚗 Car — Moncton Airport — Cynthia, Brendan, Priscilla & Thiago". Always one line per block, never a Departure+Arrival pair.
  - **Sleeping** — no leading time. Detail: the room, plus a `" till <end day>"` clause when the stretch spans more than one day (omitted for a single-day stretch — e.g. Susan's first night in the Master Suite reads just "Sleeping Cottage — Master Suite", with no "till" clause, since it's a single night) — e.g. "Sleeping Cottage — Blue Room till Tuesday, Aug 11". One line per contiguous same-room date range, in date order. Computed by walking every date from arrival (or August 1 if omitted) through the last date they're actually present for (the day before departure, if departure's quarter is `00-06` — the very first quarter of that date, meaning they're gone before any of it — otherwise the departure date itself; or August 15 if departure is omitted) and collapsing consecutive same-room dates into one range — the same `room`/`room_by_date` resolution and the same presence rule the Timeline's Structures row uses, just grouped into ranges instead of listed per night, and re-split into a new milestone if the same room recurs non-consecutively (e.g. Cottage → The Field → Cottage again shows as three separate Sleeping lines, not two, since the two Cottage stretches aren't adjacent). Any date range covered by an `excursion` (see *Data* → `excursions` above) is skipped in this walk entirely — the stay splits into two Sleeping milestones with a gap between them (and a day heading of its own for whichever date the stay resumes on), rather than one range that wrongly includes time the person was away. This page keeps the "Sleeping" label even though the Timeline's equivalent row is called "Structures" — here it's specifically framed as this person's own overnight story, not a shared live view of every structure, so the more personal label still fits.
  - **Working from** — no leading time. Detail: the structure, then its quarters (e.g. "mornings & afternoons") — **no `till <end day>` clause, ever**: unlike Sleeping, a Working from block is not summarized as a single range line. Working from a structure is true or not true on a given day, the same as any other daily fact, so it renders as **one identical line per calendar date the block covers**, `start_date` through `end_date` inclusive, each nested under that date's own day heading — e.g. a block `{ "structure": "Red Shed", "start_date": "2026-08-03", "end_date": "2026-08-06" }` (see *Home & Timeline* → *Data* → `working_from` above) produces four separate "Working from Red Shed, mornings & afternoons" lines, one under each of Aug 3rd/4th/5th/6th's own headings — not one line under Aug 3rd saying "till Aug 6". A single-day block (the narrowed-quarters exception case in *Data* → `working_from` above) is just the one-day version of this — already exactly one line, since it only ever covered one date.
  - **Departure** — same shape as Arrival. If `departure` is omitted: no leading time, detail reads "Staying past this date" (grouped under an August 15 day heading, sorting as if dated August 15).
  - **Driving** — time: as above, from the OTHER person's leg. Detail: `"<traveler's name>'s arrival/departure — <mode, hub/vehicle, detail>"`, e.g. "Rachel's departure — ✈️ Plane — Moncton Airport — 6am flight · Departing Cottage at 3am". One line for every OTHER person's leg where this person is set as that leg's `driver_id` (see *Home & Timeline* → *Data* → `driver_id` above), grouped under that leg's own date. The only fact sourced from someone else's entry, not this page owner's own — see *Data* → `driver_id` above — and the only one that can appear even when this person has no `travel.json` entry of their own (a driving obligation doesn't depend on the driver's own travel status).

## Milestones (`site/milestones/`)

### Purpose

A full-trip, all-at-once view of arrivals, departures, and meals, for the two things the Timeline's own day-quarter canvas isn't built for: skimming "who's arriving when" across the *whole* fifteen days at a glance (the Timeline only ever shows one quarter at a time), and answering "am I the only one arriving Thursday, or is everyone?" — a question that requires seeing every day side by side, not scrolled to one at a time. Purely reference, same as the Family Tree and Attendees — no editing UI, nothing entered here that doesn't already live in `timeline/data/travel.json`/`meals.json`.

### Five pages, each its own file under `site/milestones/`

Reached only via the "Milestones ▾" nav item's panel (see *Navigation* → *Milestones panel* above) — no page links to another except through that panel, and there's no index page listing all five (the panel itself is that index). In the fixed order the panel always shows them:

1. **`arrivals.html`** ("Arrivals") — every arrival across the whole trip, one flat chronological list, day-headed.
2. **`meals.html`** ("Meals") — the full `timeline/data/meals.json` plan, same shape.
3. **`departures.html`** ("Departures") — every departure across the whole trip, same shape.
4. **`arrivals-departures.html`** ("Arrivals and Departures") — arrivals and departures interleaved into one chronological list, each row tagged **Arrival** or **Departure** (see *Layout* below) so which is which is never ambiguous.
5. **`all.html`** ("All") — arrivals, departures, AND meals, all interleaved into one chronological list, each row tagged **Arrival**/**Departure**/**Meal**.

`all.html` is the superset of the other four combined — nothing appears on it that isn't also on exactly one of the other four (an excursion's `depart`/`return` each appear on both `arrivals-departures.html`/`all.html` in their own right, same as they do on `arrivals.html`/`departures.html` separately — see *Data* below).

### Data

Reads `shared/data/people.json`, `timeline/data/travel.json`, and `timeline/data/meals.json` — read-only, the same files the Timeline/Attendees already own; nothing is entered a second time for this feature.

- **Arrivals** — every attending person's own bookend `arrival`, plus every `excursion`'s own `return` leg (counts as an arrival, same as everywhere else on the site — see *Home & Timeline* → *Data* → `excursions`). Not-attending people, and anyone with no `arrival` leg at all, simply don't appear.
- **Departures** — same, for `departure` and every `excursion`'s own `depart` leg.
- **Meals** — every dated entry in `timeline/data/meals.json`, in date+quarter order.

**Grouping — several people sharing one real trip render as one combined row, not one per person** — e.g. a family landing on the same flight reads as a single "Cynthia, Brendan, Priscilla & Thiago" row. Same underlying rule the Timeline's own Arriving:/Departing: rows use (see *Home & Timeline* → *Row-by-row rules* → *Arrivals* above: same mode and identical hub/vehicle/free-text detail/driver, or — with nothing else distinguishing the shared time — actual partners only), just computed across the *whole trip* instead of one quarter at a time, so the exact date+quarter+`time_range` has to be part of what counts as "the same trip" here too (two flights that happen to land in the same broad quarter, e.g. 6:30pm and 11:55pm both "Evening," are never the same trip just because they share a hub — the same reasoning the Attendees page's own "with `<names>`" clause already established, see *Attendees* → *Layout* above). A `dogs` tag rides along inline on whichever name it belongs to, same as the Timeline's own rows.

### Layout

Nav bar per *Navigation* above (the same five items as every other page). Below it: an `<h1>` title (the page's own name, e.g. "Arrivals") and a one-line subtitle, then the list itself in `<main>`.

**One `<h2>` day heading per distinct date** (full weekday + abbreviated month + ordinal day, e.g. "Wednesday, Aug 5th" — the exact same `format_date_full()` and the exact same day-heading markup the Attendees page's own timeline uses, moved to `shared/base.css` so both features share one definition rather than two copies that could drift), every row for that date nested underneath it, in date+quarter+time order — not a flat list repeating the date on every row.

Each **arrival/departure row**: the mode emoji (✈️/🚆/🚗), the resolved time (exact `time_range` if set, else the bare quarter name, else — for `00-06`, which has no name of its own, see *Terminology* — its own bare time range), the grouped names (see *Data* → Grouping above; a partner-pair or larger group joined the same plain-English way as everywhere else on the site, e.g. "Ann, Bo & Cy"), then any further detail (hub/vehicle/free-text detail/driver, worded "pickup"/"driving" exactly as the Timeline's own rows and the Attendees page's own driver_id text already do — see *Home & Timeline* → *Data* → `driver_id` above), then a **"Timeline"** link straight to that exact quarter screen (`../index.html#qc-...`).

Each **meal row**: the quarter name (or bare time range for `00-06`), the meal's own `note`, its tagged `structure` if one is set, and a **"Timeline"** link to that quarter screen too.

**On `arrivals-departures.html`/`all.html` only**, each row additionally leads with a small kind tag — **Arrival**, **Departure**, or **Meal** (same `.fact-label` treatment the Attendees page's own fact labels use) — so a reader scanning the merged list always knows which kind of row they're looking at without having to infer it from the row's own shape. Omitted on the three single-kind pages, where the whole page already says what it is.
