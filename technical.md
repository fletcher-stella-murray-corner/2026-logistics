# Technical Architecture

How this project is actually built: the single-repo structure, the build pipeline, what every script does, and where a CSS/JS/markup change belongs. This is architecture reference, not process — for how we (human + AI) actually work together (the requirements-doc loop, git rhythm, milestone tracking), see `way-of-working.md`. For account/domain/hosting facts, see `operations.md`.

## Shape of the system

- One site, one repo: the public site (`site/`) plus every feature's source (data, scripts, shared CSS/JS) live together — see `requirements/public.md` for what the site does, and *Repo & deployment* below for hosting. There is no admin/data-entry site; the sole editor edits data files directly and reruns the build.
- No runtime backend. Every page is a **build artifact**: a Python script renders static HTML directly from a feature's data file(s) at build time, so pages open via `file://` or a static host with nothing to serve and nothing to keep alive.
- No npm, no bundler, no framework. Each feature's `build.py` (and `scripts/build_site.py`, which calls every feature's build script in one go) is the one build step, and is the intentional exception to that rule — it's plain Python 3 with no dependencies.
- `.claude/launch.json` (committed, not gitignored) defines local static-server configs for AI-tool browser-preview integrations to serve pages over HTTP during a session. This doesn't change anything above: pages still open directly via `file://` with nothing to serve, this is just a convenience for previewing in a browser sandbox that can't load `file://` URLs.

## Repo & deployment

One GitHub repo, `fletcher-stella-murray-corner/2026-logistics`, holds everything: source data, scripts, docs, and the built `site/` output. It can be private or public — either way, GitHub Pages can serve from it.

**Deploying:** a GitHub Actions workflow (`.github/workflows/deploy.yml`) publishes the contents of `site/` to GitHub Pages on every push to `main`. Before it deploys, a `verify-build` job reruns `scripts/build_site.py` from the committed data and fails the workflow (no deploy) if the regenerated `site/` differs from what was pushed — catches a data/template edit committed without rerunning the build, a hand-edited `site/` page, or invalid data that a local run of `build_site.py` would have caught. There is no manual deploy script and no second repo — commit and `git push`, and the live site updates a minute or two later once the check passes. One-time setup: in the repo's Settings → Pages, set *Source* to "GitHub Actions" (see `operations.md`).

**Normal update flow:** edit a data file (or run a feature's `build.py` after hand-editing it), review the regenerated page locally, commit, push. See `way-of-working.md` → *Git*.

## Scripts

Every script lives in a feature's `scripts/` folder, is plain Python 3 with no dependencies, and should support `-h`/`--help`.

**Data entry** — there is no add/set script pair. The sole editor (you) hand-edits a feature's JSON data file directly, then reruns its `build.py`. See each feature's data file structure in `requirements/public.md`.

**Build** — regenerate HTML from data. Run after hand-editing a data file or changing a page template.

**Review** — a read-only cross-person consistency check, run after data entry and before committing (see `way-of-working.md` → *Data entry*). Distinct from Build: a clean `build_site.py` run only proves each record is well-formed on its own, not that it still agrees with everyone else's.

## The Structures stage

Every page on this site is otherwise inert once built — HTML rendered once at build time, nothing re-rendered client-side (see *Shape of the system* above). The Structures stage (`requirements/public.md` → *Home & Timeline* → *The Structures stage*) is the one place that pattern gets extended, not abandoned — and its mechanism went through three real design iterations before landing here; the third is what's actually shipped. The first two are worth keeping on record because each one's own failure is exactly what the next iteration was built to close:

- **First version (retired): one pre-rendered frame per quarter, whole-frame swap.** `timeline/scripts/build.py` computed one full box tree per quarter (`render_structures_frame()`) and JS toggled which whole frame was visible. This fixed the original "flying by" problem (a structure box no longer re-rendered fresh inside every quarter screen), but review caught two real regressions it introduced: a horizontal-scroll layout for overflow (bad on a phone — a second, sideways gesture competing with the page's one, scroll-is-time interaction), and visible box-shifting as occupant text length changed, since each frame's `.structure-boxes` was a `flex-wrap: nowrap` row where any box's width change shoved every box after it sideways.
- **Second version (retired): a fixed set of independently-mounted slots, no per-quarter frames.** `timeline/scripts/build.py` → `compute_structures_stage()` derived, once, the full set of structure/building/room/instance/Working/Kitchen/Unassigned slots EVER relevant anywhere in the trip, each rendered as exactly one permanent HTML element carrying its own `data-mount-from`/`data-mount-to` (a "qc-..." screen-id range — see `quarter_screen_id()` in `shared/trip.py`), plus one hidden `<span class="room-people">` variant per contiguous same-text run (`compact_runs()`). This fixed the previous version's sideways-shove problem (nothing re-rendered fresh inside a quarter screen any more), but "mounted"/"unmounted" here still meant the native `hidden` attribute — `[hidden] { display: none }` — toggled on and off an element's *entire lifetime*: absent from layout before its own first relevant quarter and after its last, present only in between. Review correctly rejected this as still broken, for a reason the previous fix didn't touch at all: `display: none` removes an element from layout FLOW, not just from view, so the moment ANY slot's own relevant window opened or closed, its container (a CSS grid or flex row) reflowed everyone after it — and because `#structures-stage` is bottom-anchored (`position: fixed; bottom: 0`) with no height cap, ANY change to its total height shifts its own top edge, which shifts *everything already on it*, even a slot whose own content never changed. Verified directly at the time: Cottage's position relative to the stage stayed pixel-perfect across dozens of quarters, but the instant Blue Room mounted for the first time inside Cottage's own box, Master Suite's viewport-relative position shifted by that exact height delta, despite Master Suite's own content never changing.
- **Current version: the complete map is in the DOM and in its final layout position from the very first paint — only visibility ever changes, never presence.** The relevance-window computation is unchanged from the previous version (`compute_structure_relevance_windows()`, `structure_relevant()`, `room_relevant()` still walk every quarter of the trip exactly once, up front, in `compute_structures_stage()`) — what changed is what an element's own window means once it's known. Every structure, building, room/instance, Working, and Kitchen sub-box (plus the top-level Unassigned box) that will EVER be relevant anywhere in the trip is rendered exactly once, unconditionally, and stays in the DOM — in its own fixed position within `.structures-stage-inner`'s grid, or a `.structure-rooms`/`.building-rooms` flex row — for the entire time `#structures-stage` itself is visible, i.e. from the moment a visitor scrolls off Home/the transition screen through the last quarter of the trip. There is no more mounting or unmounting *any* individual slot; "is this place currently relevant" is now a pure visibility question, never a layout one:
  - Every element still carries its own `data-mount-from`/`data-mount-to`, but `timeline/shared.js` → `applyStructuresMountRanges(currentId)` now toggles a `slot-dark` class instead of the native `hidden` property for everything *except* `#structures-stage` itself — `.slot-dark { opacity: 0.15; pointer-events: none }` (`timeline/shared.css`), not `display: none`, and — after a review pass — not `visibility: hidden` either. The first fix used `visibility: hidden`: it doesn't remove an element from layout the way `display: none` does (the browser still reserves exactly the space it would take up if visible), which was the entire point, but it DOES remove the element from view, from screen readers, and from the tab order — a dark place vanished completely, which review correctly flagged as not what "the map is a building directory, not a light switch" (`brand-guidelines.md` → *Materials / Design Language*) actually calls for: a not-yet-relevant place should still be faintly LEGIBLE as part of the map, not gone. `opacity` is the fix that satisfies both: like `visibility: hidden`, it doesn't remove the element from layout (the reservation is unaffected either way); UNLIKE `visibility: hidden`, it doesn't remove the element from view — a dark box paints, just at 15% strength, a ghost rather than an absence. `pointer-events: none` keeps it inert (nothing to tap on an irrelevant place), and `timeline/shared.js` separately toggles `aria-hidden` alongside the class so a screen reader still skips announcing it, matching what `visibility: hidden` used to give for free. Either way, a slot's box occupies its own spot in the grid/flex row from build time onward, whether it's currently lit (full strength) or dark (ghosted) — going from one to the other changes nothing about anyone's position, because nothing was ever added to or removed from the layout to begin with.
  - `#structures-stage` itself is the one deliberate exception, and keeps the native `hidden`/`display: none` toggle for the whole-strip Home/transition-screen-vs-Timeline swap (`applyCurrentScreen()` in `timeline/shared.js` still sets `.hidden` directly on it, not the `slot-dark` class) — safe to remove entirely from flow because it's `position: fixed`, already outside document flow, so hiding the whole thing can't reflow anything else on the page the way hiding a flow-participating child would.
  - **The identical problem existed for occupant *text*, not just box existence, and needed the identical fix — with one deliberate exception to the ghost treatment above.** The previous version's own hidden `<span class="room-people">` variants were also toggled via `hidden`/`display: none` — so a room-slot's rendered width and height were always driven by whichever ONE variant currently had `display` other than `none`, meaning a room's box could visibly grow or shrink *within its own already-lit window* as its occupant list changed length, and — since these boxes sit in wrapping flex/grid rows — could shove neighboring boxes around exactly the same way the box-mounting bug did. `render_text_variants()` (and the `working_variants()`/`kitchen_variants()` closures inside `compute_structures_stage()`) now wrap every slot's own pre-rendered variants in one `<span class="room-people-variants">` container (`display: grid`), with every variant span placed in the SAME grid cell (`grid-area: 1 / 1`) and toggled via the same `slot-dark` class as everything else — but `.room-people.slot-dark` is overridden back to `visibility: hidden` (not the ghost `opacity` every BOX-level dark element gets), specifically because every variant for a slot shares that one grid cell: if more than one were faintly visible at once (ghosted, not gone) their text/chips would visibly overlap into an unreadable mess. Only the box itself (room/building/structure) reads as a ghost when dark; its own occupant content is either fully shown (the one current variant) or fully absent (every other variant, all at once when the box itself is dark and has no current variant to begin with) — never partially, faintly visible the way the box's own border/label are. A CSS grid track auto-sizes to the largest INTRINSIC size among every item assigned to it, regardless of that item's own visibility — so the container's width and height are permanently fixed to the max across every variant that slot will EVER show, from the very first render, whether or not that variant is the one currently visible. A room now reserves enough space for its own longest-ever occupant list up front; a shorter list just leaves visible blank space inside an otherwise-unchanging box, the identical "reserve ahead of need" trade-off applied one level deeper than box existence. This closes the Blue Room/Master Suite trade-off the previous version's own docs flagged as unfixed, and a width-based version of the same bug that version never actually caught.
  - **This relies on one real invariant, not enforced by CSS itself: a lit descendant's own range is always fully contained within its lit ancestor's.** Unlike `visibility` (which a descendant CAN explicitly re-override back to visible even under a hidden ancestor), `opacity` offers no such escape hatch — it composites: a child's own rendering happens INSIDE the stacking context its ghosted parent already created, so a lit room nested inside a dark (0.15-opacity) structure would render at a visually compounded, wrongly-faint strength no matter what the room's own class says, with no CSS-only way to "undo" the parent's dimming from the child side. This never actually happens, by construction: `compute_structure_relevance_windows()` touches a structure's own window at the exact same quarter it touches one of that structure's room windows (see that function's `touch()` calls), a building's own range is the union of its rooms' ranges, and a `permanent` structure's range (`structure_active()`) spans its whole `active_from`/`active_to` window, which trivially contains any narrower room window inside it. A structure/building box is therefore always at least as "lit" as everything nested inside it, at every quarter — so the compounding risk is real in principle but never triggered in practice. Worth re-checking if the relevance-window computation ever changes; unlike the old `visibility`-based version of this same guarantee, there's no cheap "just add an explicit override" fallback available if it ever did break.
  - `timeline/shared.js` still needs no per-quarter lookup map — `applyStructuresMountRanges(currentId)` walks the same cached array of `[data-mount-from]` elements and does the identical plain string comparison (`from <= currentId <= to`) it always did; only what it sets in response changed.
- **Reuses the nav label's own `IntersectionObserver`, not a second one — but only as a trigger, not as the source of truth.** Unchanged from the previous version: the observer's callback ignores its own `entries` batch entirely (a real, confirmed bug — see git history — came from trusting a batch that only reports elements whose OWN state changed since the last callback, not the full current truth) and is purely a "something changed, go check" trigger. The real answer always comes from `currentQuarterScreen()`, a synchronous geometry walk (also used by the settle-time correction and the play/pause control) that re-derives the true current screen from scratch every time.
- **Hiding the stage (and every currently-lit slot inside it) on Home/the transition screen still falls out of the same mechanism for free** — `currentId` is `''` there (no current quarter), and `from <= '' <= to` is false for every real range, so every descendant slot goes dark and `#structures-stage` itself goes `hidden`; no special-cased "stage container" logic needed beyond giving it the same `data-mount-from`/`data-mount-to` attributes (spanning the whole trip) as everything nested inside it.
- **Still no height cap, no scroll region of its own** (a deliberate call, not a default — `requirements/public.md` flags the reasoning) — but what "no cap" now reserves is a materially bigger, and fixed, quantity than before: not "however many structures are relevant at any one quarter" (small, and constantly changing), but the full set of EVERY structure/building/room/instance/Working/Kitchen box relevant at ANY point across the whole trip, all reserved simultaneously, all the time, the instant the stage first becomes visible. Concretely, for this trip's own data (`shared/data/structures.json`): 7 accommodation structures, one of which (Little Shemogue Inn) alone reserves 2 building-slots holding 5 room-slots between them, another (Cottage) reserves 3 room-slots plus a Kitchen sub-box, another (Red Shed) reserves a Working sub-box — roughly 18–20 always-present boxes stacked in the single-column mobile layout, most of them dark at any given quarter. `.quarter-canvas`'s own bottom-padding reservation (`timeline/shared.css`) still reads a live `--stage-height` custom property kept in sync by a `ResizeObserver` on `#structures-stage`, but that observer's job is narrower now: the stage's height no longer changes as a *consequence of scrolling through quarters* at all (nothing mounts or unmounts anymore, ever, once first rendered), so the observer is only still needed for a genuine viewport-driven reflow — a window resize crossing one of `.structures-stage-inner`'s column-count breakpoints, a mobile browser's chrome collapsing/expanding, or a late-loading font nudging text-wrap points. Worth keeping (cheap, and those are all real events), but no longer covering for the thing it originally existed to cover for.
  - **Measured directly, this was worse in practice than the design discussion anticipated, and got a real follow-up fix.** On a 375×812 phone viewport (measured via `getBoundingClientRect()`, not eyeballed — a screenshot alone doesn't reveal a fixed element's true height reliably, see *Lessons learned* below), the stage came in at 1177px against an 812px screen — 45% taller than the viewport, with no scroll region to reach the rest: since `#structures-stage` has no `overflow` handling and is taller than the screen, whatever chunk of it happens to render is all a visitor can ever see, permanently covering the ENTIRE viewport (including the scrolling quarter canvas and its time-of-day background — see *Time-of-day background* — sitting invisibly behind it). Two real fixes landed together to close most of that gap: (1) a person's name renders as a small tap-to-reveal initials chip (`render_person_chip()` in `timeline/scripts/build.py`, `<details>`/`<summary>` reusing `shared/nav.py`'s own jump-menu disclosure element and `shared/nav.js`'s existing "close other open disclosures" handling — see `requirements/public.md` → *The Structures stage* → *Nested box display* and brand-guidelines.md → *Illustration / Imagery Style*), not the plain name; and (2) every box's own padding/font-size/gap was independently tightened, since measurement showed the chip alone barely moved the needle (1177px → 1141px) — the real cost was the fixed "shell" (border, padding, label) on ~20 always-reserved boxes, not any one occupant's text length. Together: 1177px → 835px, a 29% reduction — still 23px (2.8%) over an 812px viewport, an honestly-reported remaining gap, not rounded away, and one a wider phone (390–430px is now the more common width) already closes on its own since more chips/rooms fit per row before wrapping. Chasing the last few pixels further wasn't worth shrinking type past what's legible "in bad light, one-handed" (`brand-guidelines.md` → *Audience*) — a diminishing-returns call, not an oversight.
  - **Chip sizing reuses the exact grid-overlay mechanism described above, with one simplification.** `render_variant_chips()` (parallel to `render_variant_spans()`, and used for everything render_variant_spans() ISN'T — a room/instance/bare-structure's occupants, a Working sub-box's name list; Kitchen's own note stays on `render_variant_spans()` unchanged, since a meal note is prose, not a person list) still runs every compact_runs() run through the same `.room-people-variants` shared-grid-cell reservation — but a chip's own footprint is uniform (a fixed-size circle) where free text wasn't, so what actually varies from run to run is just the COUNT of chips, not their individual widths. `compact_runs()` itself needed no change at all: it only ever compares consecutive values with `==`, and a tuple of names compares exactly as well as the joined string it replaced.
- **Multi-screen jumps reuse `jumpToSection()`'s `window.__scrollJumpActive` flag** (`shared/nav.js`): set only for a jump that actually crosses more than one quarter screen, never for an adjacent one. `applyStructuresMountRanges()` is skipped for the duration via the same observer-callback guard the nav label uses, and `window.__syncStructuresStage()` settles it directly on the destination's correct lit/dark state in one step once the jump lands (see `shared/nav.js` → `jumpToSection()`'s own `settle()`).

## Where CSS and JS changes go

- **`shared/base.css`** — site-wide chrome shared by every feature: nav bar, color variables, base typography. Change here affects every page.
- **A feature's `shared.css`** (e.g. `timeline/shared.css`) — CSS specific to that feature's page(s) only (day quarter canvas layout, family-tree diagram styling).
- **Inline `<style>`/`<script>` in the page** — page-specific setup only: rendered content and any page configuration constants. Nothing else belongs here.

When in doubt: if a change would need to be made in more than one page, it belongs in `shared/base.css` (site-wide) or the owning feature's `shared.css` (feature-wide), not copied into each page's inline block.

**Changing what shape a data file is** (a new/renamed/removed field, a new allowed value, a whole new file) is a different question from where CSS/JS goes — see `way-of-working.md` → *Data model changes* for that procedure.

**After editing any of these, run `scripts/build_site.py` before previewing.** No page in `site/` links to `shared/base.css` or a feature's `shared.css`/`shared.js` at runtime — the build step inlines their contents into each page's `<style>`/`<script>` block (see *Shape of the system* above). Editing a source file and reloading a page already open from `site/` will show zero change, no matter how correct the edit is — the browser is still rendering whatever was embedded at the last build.

## Lessons learned

**Cross-page nav links must account for folder depth.** `site/family-tree/index.html` is one directory below `site/index.html`, so its link back to the Timeline must be `../index.html` — a bare `index.html` resolves against the *current* directory and silently links the page to itself (no 404, no console error, just a dead "back" link that looks fine until you actually click it). The rule going forward: any relative href between two pages needs to account for the actual path difference between them — `family-tree/index.html` or `attendees/<id>.html` from the root, `../index.html` from one directory down (`family-tree/` or `attendees/`), `../attendees/<id>.html` from `family-tree/` to `attendees/` (and vice versa). Caught only by actually clicking the link and checking `location.href`, not by reading the code — the href *looks* correct at a glance either way.

**`attendees/scripts/build.py` never deletes a stale output file — only ever writes/overwrites the ones it currently generates.** Its output filename is `<id>.html`, so any change to a person's `id` (a renumber, or the one-time migration to random 6-digit ids — see `requirements/public.md` → *people.json* → `id`) leaves the *old* `<old-id>.html` sitting in `site/attendees/` untouched, alongside the new `<new-id>.html` — a real, still-deployed, now-orphaned page with no link pointing at it from anywhere on the site, easy to miss since the build itself exits clean and every *linked* page looks correct. After any change that alters which ids exist, diff `site/attendees/`'s file list against the current `attending: true` roster and delete anything left over by hand — this isn't automated.

**A flag that's set and cleared but never read fails silently, with no build error to catch it — and a comment describing behavior the code doesn't actually implement is just as easy to trust by mistake.** `shared/nav.js`'s `jumpToSection()` sets `window.__scrollJumpActive` before a multi-screen jump so `timeline/shared.js`'s live time-of-day blend can suspend itself for the jump's duration (see `requirements/public.md` → *Time-of-day background* — a jump of more than one quarter screen must show no color changes in transit, only the destination's correct color; a jump of exactly one screen still plays the blend, same as organic scrolling). Two independent gaps were found here together, on the same two lines of code: `timeline/shared.js`'s blend code never actually checked the flag (`scheduleQuarterBlendUpdate()`/`updateQuarterBlend()` ran unconditionally on every `scroll` event, jump or not — now fixed, both functions bail early while the flag is set), and `jumpToSection()` set the flag unconditionally for every jump regardless of distance, even though its own comment directly above claimed otherwise ("nothing skipped for a single-screen jump... since those never set this flag") — now fixed via `isMultiScreenJump()`, a plain bounding-rect distance check against the target *before* scrolling starts. Neither gap was caught by the build (this is pure client-side JS with no test harness) or by re-reading the comments (the comment for the second gap was simply wrong, not missing). The rule going forward: whenever a new live-updating effect is wired to `scroll`/`IntersectionObserver` (the Structures stage's frame-toggle, see *The Structures stage* above, is the next one), verify by actually triggering the behavior in a browser, not by re-reading the comment that claims it works.

## Architecture boundary

This repo does not depend on other projects or systems on the machine (other codebases, a personal planning/documentation system, global tool config) to be built, deployed, or understood — everything needed is in this repo. If that ever stops being true (a script starts reading from outside the repo, a doc's meaning depends on external context), that dependency must be called out explicitly wherever it's introduced — in the relevant doc, not left implicit.
